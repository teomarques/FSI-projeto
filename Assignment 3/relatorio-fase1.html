1. Introdução

Este relatório documenta os resultados dos testes de segurança realizados sobre a aplicação web OWASP Juice Shop, seguindo as diretrizes do OWASP Web Security Testing Guide (WSTG v4.2). O objetivo é identificar e documentar vulnerabilidades presentes na aplicação, bem como demonstrar de que forma estas podem ser exploradas.

Os testes foram realizados numa abordagem black-box, sem conhecimento prévio do código-fonte ou da arquitetura interna da aplicação, recorrendo a ferramentas de segurança como o OWASP ZAP e técnicas de penetration testing manual.

17. Conclusões da Fase 1

A análise de segurança do OWASP Juice Shop revelou múltiplas vulnerabilidades críticas que comprometem completamente a segurança da aplicação:

  1. A vulnerabilidade de SQL Injection no formulário de login permite acesso imediato à conta de administrador sem qualquer credencial válida.
  2. A password fraca do administrador (admin123) foi descoberta em segundos por um ataque de força bruta simples.
  3. O painel de administração expõe dados de todos os utilizadores sem controlos de acesso adequados.
  4. A configuração CORS permissiva e a ausência de cabeçalhos de segurança (CSP, X-Frame-Options) aumentam significativamente a superfície de ataque.

Estas vulnerabilidades serão abordadas na Fase 2 através da implementação de um WAF com Apache2 + ModSecurity + OWASP CRS.

4.1.1 Componentes Instalados

ComponenteVersão/DetalheFunção
Apache HTTP Server (httpd)CentOS 9Servidor web e proxy reverso
ModSecuritymod_security (CentOS repo)WAF – motor de inspeção de pedidos HTTP

4.1.2 Configuração do Proxy Reverso

Ficheiro: /etc/httpd/conf.d/juiceshop-waf.conf

<VirtualHost *:80>
    ServerName 192.168.100.30
    ProxyPreserveHost On
    ProxyPass        / http://192.168.100.20:3000/
    ProxyPassReverse / http://192.168.100.20:3000/
    Header always set X-Frame-Options "SAMEORIGIN"
    Header always set X-Content-Type-Options "nosniff"
    Header always set X-XSS-Protection "1; mode=block"
    ErrorLog  /var/log/httpd/juiceshop-error.log
    CustomLog /var/log/httpd/juiceshop-access.log combined
</VirtualHost>

4.1.3 Configuração do ModSecurity

Ficheiro: /etc/httpd/conf.d/mod_security.conf

  • SecRuleEngine: On (modo bloqueio — bloqueia pedidos maliciosos)
  • SecRequestBodyAccess: On (inspeção do corpo dos pedidos HTTP)
  • Inspeção de JSON: Ativada com regra personalizada (id:900001) — necessária para detetar payloads em Content-Type: application/json
  • OWASP CRS: Regras carregadas em /etc/httpd/modsecurity.d/activated_rules/, incluindo REQUEST-942-APPLICATION-ATTACK-SQLI.conf e REQUEST-949-BLOCKING-EVALUATION.conf

4.4 WSTG-IDNT – Identity Management Testing (através do WAF)

Não aplicável ao WAF
Conforme indicado no enunciado (secção 6, ponto 2), os problemas identificados na secção 4.3 do WSTG (Identity Management) não podem ser detetados nem resolvidos com ModSecurity (OWASP CRS). 4.8b Novos Alertas Introduzidos pelo WAF

Multiple X-Frame-Options Header Entries (880 instâncias) — PROBLEMA INTRODUZIDO PELO WAF
O WAF adiciona o cabeçalho X-Frame-Options: SAMEORIGIN através da configuração do VirtualHost. Porém, o JuiceShop já envia o mesmo cabeçalho nas suas respostas. O resultado são dois cabeçalhos X-Frame-Options duplicados, o que constitui um novo alerta de risco médio detetado pelo ZAP.
Solução: Usar Header always set com a diretiva always e remover o duplicado, ou usar Header always unset X-Frame-Options antes de definir o novo valor.
Fase 1: não presente | Fase 2: introduzido pelo WAF
Server Leaks Version Information via "Server" HTTP Response Header (24637 instâncias) — NÃO MITIGADO
O Apache no WAF expõe informação de versão no cabeçalho Server: (ex: Apache/2.4.x (CentOS)). Este alerta não existia na Fase 1 (o JuiceShop não expunha este cabeçalho). O elevado número de instâncias deve-se ao volume de pedidos do scan.
Solução: Adicionar ServerTokens Prod e ServerSignature Off ao httpd.conf.

5. Conclusões

Este trabalho permitiu explorar de forma prática os dois cenários do PA#3 de FSI 2025/2026: a análise de segurança de uma aplicação web (Fase 1) e a implementação de um WAF para mitigação das vulnerabilidades encontradas (Fase 2).

Fase 1 – Principais Conclusões

  • O OWASP Juice Shop apresenta vulnerabilidades críticas que comprometem completamente a sua segurança, nomeadamente SQL Injection no formulário de login e password de administrador trivialmente fraca.
  • Foram identificadas 18 vulnerabilidades distribuídas por 9 das 11 categorias WSTG, cobrindo desde falhas de configuração (CORS, CSP) até falhas de controlo de acesso e gestão de sessão.
  • As ferramentas OWASP ZAP (scan automatizado, ativo e fuzzer) e testes manuais revelaram-se complementares — o ZAP identificou padrões em larga escala enquanto os testes manuais confirmaram exploitabilidade real.

Fase 2 – Avaliação do WAF (Scan ZAP 22/05/2026 contra 192.168.100.30)

  • O WAF Apache2 + ModSecurity + OWASP CRS bloqueou com sucesso o SQL Injection de login bypass (' OR 1=1--), a vulnerabilidade crítica mais grave encontrada na Fase 1, com resposta 403 Forbidden e anomaly score SQLI = 8.
  • O scan ZAP via WAF detetou ainda 5 instâncias de SQL Injection em outros endpoints da API REST, indicando que o CRS v3.3.5 não cobre todos os vetores de injeção específicos do JuiceShop.
  • Foi necessária configuração adicional (requestBodyProcessor=JSON) para que o ModSecurity inspecionasse corretamente pedidos com Content-Type: application/json, demonstrando a importância de adaptar a configuração à aplicação alvo.
  • O WAF introduziu dois novos alertas não presentes na Fase 1: Multiple X-Frame-Options Header Entries (880 instâncias — cabeçalho duplicado por ambos WAF e JuiceShop) e Server Leaks Version Information (24637 instâncias — cabeçalho Server: do Apache a expor versão). Estes problemas são facilmente corrigíveis com ServerTokens Prod e Header always unset.
  • O WAF não consegue mitigar vulnerabilidades de lógica aplicacional (passwords fracas, broken access control em rotas Angular /#/, Identity Management) — estas requerem correções ao nível do código da aplicação.
  • A adição de cabeçalhos de segurança HTTP pelo WAF (X-Frame-Options, X-Content-Type-Options, X-XSS-Protection) melhora a postura de segurança client-side, tendo eliminado os alertas de Missing Anti-clickjacking Header nos endpoints corretamente processados pelo proxy.
  • O WAF funciona como uma camada de defesa adicional eficaz contra ataques de injeção baseados em padrões HTTP, mas não substitui boas práticas de desenvolvimento seguro.
